# Container Image: design

Third of three sub-projects that let the app run as a self-hosted container alongside the existing AWS deployment: **Storage Interface** (merged, PR #85), **Portable Auth** (merged, PR #88) and **Container Image** (this spec). The AWS deployment (Lambda, DynamoDB, Auth0) is untouched and keeps deploying from `yarnBuild.yml`.

## Intent

Ship one image that a person, or a hosting partner such as PikaPods, can run with a single volume and a few environment variables, and that gives them the full app with the built-in login, SQLite storage and optional automatic HTTPS. Success means:

- `docker run -v data:/data -p 8080:8080 <image>` serves the app. The first-run setup (account, setup code from the log) works in the browser, and data and the session survive a container restart and an image upgrade.
- With `TLS_DOMAIN` set, the same image serves HTTPS on 80/443 with certificates it obtains and renews itself.
- The container runs the **same handler code** as the Lambda: no second implementation of any route.
- A daily backup is taken without any setup, and a user can restore from it.

This serves the self-hosting and hosting-partner plan: each user holds their own data, and the author only publishes software.

## Decisions

| Question | Decision |
|----------|----------|
| Push reminders in v1 | Deferred to a follow-up. The image ships without them; the notification control stays hidden when no VAPID public key is configured. (The follow-up needs the key in the runtime `/config.json` and an in-process scheduler; the maintenance timer below is its foundation.) |
| HTTPS | Inside the image, optional. Caddy is bundled and started by the Node server only when `TLS_DOMAIN` is set. Without it the server speaks plain HTTP (hosting partners, localhost, homelab). |
| Certificate sources | Automatic (ACME) only in v1. No bring-your-own certificate files, no DNS-challenge or wildcard certificates. |
| Request path | A thin adapter over the existing handlers using `node:http` only: build an API Gateway v2 event, call the real `api-handler` and `src/static/handler.ts`, write the result back. No web framework. |
| Publishing | New workflow `container.yml`. Version tag `v*` publishes `X.Y.Z`, `X.Y` and `latest`; a push to `main` publishes only `edge`; pull requests build without pushing. GHCR, `linux/amd64` + `linux/arm64`. |
| Backups | A built-in `store-cli backup` command plus an automatic daily backup inside the container (default 03:00, newest 7 kept, integrity-checked). Same-volume backups are not off-site; the docs say so. |
| Location of new code | `container/` (the existing `server/index.ts` is an unrelated old Lambda handler). |

**Not doing (on purpose):** push reminders and a runtime VAPID key, bring-your-own certificates, DNS-challenge or wildcard certificates, tiered backup retention, off-site backup upload, a `restore` command (restore is documented as stop, replace the file, start), Postgres, multi-user, generic OIDC, Demo Mode, Kubernetes manifests, a metrics endpoint, and per-client login throttling (the global throttle stays, as documented in `SECURITY.md`).

## 1. Runtime

### Process model

`tini` runs as PID 1 and starts the Node server (`container/server.ts`, compiled with `tsc --module commonjs --strict` like the other handlers). When `TLS_DOMAIN` is set the server spawns Caddy as a child process using a Caddyfile it generates at boot. If Caddy exits, the server exits so the orchestrator restarts the container. The container runs as a non-root user (uid 10001); the Caddy binary has `cap_net_bind_service` so it can bind 80 and 443.

### Boot sequence

Fails fast with a clear message at each step:

1. Validate the environment (table below).
2. `initStore()` on `$DATA_DIR/budget.sqlite`. It refuses a database whose `PRAGMA user_version` is newer than the code understands.
3. `initAuth()` with `AUTH_MODE=local`. This logs the setup code when no account exists, so it is visible in `docker logs` straight after start (closes the Portable Auth parked item).
4. If the newest backup is more than a day old (or none exists), take one now (catch-up).
5. Start the maintenance timer: hourly `purgeExpired()`, daily backup.
6. Listen. Then start Caddy if `TLS_DOMAIN` is set.

`GET /healthz` answers 200 only after boot and after a trivial database read; the Dockerfile `HEALTHCHECK` calls it with Node (no `curl` in the image).

### Requests

- The adapter lower-cases header names, sets `cookies` from the `Cookie` header, `rawPath`, `body`, `requestContext.http.method` and `routeKey`, and writes `statusCode`, `headers`, `body` (base64-decoded when flagged) and each `result.cookies` entry as a `Set-Cookie` header.
- `GET /config.json` is generated by the server as `{"auth":"local"}` and takes precedence over any file in `build/client`.
- Static files and the Content-Security-Policy come from the existing static handler.
- The frontend is built into the image with fixed dummy `VITE_AUTH0_*` values (as the screenshot harness does). They are never used because the runtime config overrides them, and no real tenant is ever baked in.

### Configuration

Environment variables only.

| Variable | Default | Meaning |
|---|---|---|
| `DATA_DIR` | `/data` | Volume with the database, backups and `caddy/` certificate storage |
| `PORT` | `8080` | Node listen port (loopback only when Caddy is on) |
| `TLS_DOMAIN` | unset | Set for automatic HTTPS on 80/443; unset means plain HTTP |
| `TLS_EMAIL` | unset | Optional ACME contact address |
| `APP_ORIGIN` | `https://$TLS_DOMAIN` when set | The public URL. When set, the Origin check requires an exact match |
| `TRUST_PROXY` | on with Caddy, off otherwise | Honour `x-forwarded-*` headers |
| `COOKIE_SECURE` | derived | `Secure` exactly when the effective origin is `https`; one logged warning when there is no effective origin. An explicit `true` or `false` overrides the derivation (for a user behind their own HTTPS proxy who has not set `APP_ORIGIN`) |
| `BACKUP_HOUR` / `BACKUP_KEEP` / `BACKUP_DIR` | `3` / `7` / `$DATA_DIR/backups` | `BACKUP_KEEP=0` turns backups off |
| `TZ` | `UTC` | Timezone for the backup hour |

The server sets `AUTH_MODE=local`, `STORE=sqlite` and `SQLITE_PATH` itself; users do not.

## 2. Image, build and CI

### Dockerfile

Multi-stage, every base pinned by digest.

- **Build stage:** `node:24-bookworm-slim`. `yarn install --frozen-lockfile`, build the SPA (dummy `VITE_AUTH0_*` only if the build needs them), compile the container server (which pulls in the API handler and the static handler) and the `store-cli`. The Lambda-only `build-static-handler.cjs` step is not run; the container uses `createStaticHandler` directly.
- **Runtime stage:** the same slim image plus `tini`; the `caddy` binary copied from the official image (digest-pinned) with `cap_net_bind_service`; the non-root user; `VOLUME /data`; `EXPOSE 80 443`; OCI labels for source (the repo) and licence (AGPL-3.0); the `HEALTHCHECK`.
- **Runtime dependencies:** expected to be near zero. Local mode uses only `node:sqlite` (built in); the AWS SDK and the Auth0 libraries are required lazily and never loaded here, so they are left out of the image. The plan verifies this by running the smoke test against an image without them.

### Source offer (AGPL)

The image carries the OCI `source` label and the About page gets a small "Source code" link to the repository.

### CI: `.github/workflows/container.yml`

`yarnBuild.yml` and the AWS deploy are not changed.

| Trigger | Behaviour |
|---|---|
| Pull request | Build `linux/amd64` without pushing; run the smoke tests |
| Push to `main` | Build `amd64` + `arm64` (buildx + QEMU), scan, push `edge` to GHCR with provenance and an SBOM |
| Tag `v*` | The same, pushing `X.Y.Z`, `X.Y` and `latest` |

- **Smoke test** (`scripts/container-smoke.mjs`, no browser): run the container with a temporary volume; `/healthz` is 200; `/config.json` is `{"auth":"local"}`; `/api/auth/status` reports setup required; setup succeeds with the code scraped from `docker logs`; login works; after a container restart the data and session persist; `store-cli backup` writes a file that passes `PRAGMA integrity_check`.
- **HTTPS smoke test:** a second run with `TLS_DOMAIN=localhost`. Caddy issues from its internal CA with no internet needed. It checks HTTP redirects to HTTPS and that the `Secure`, `__Host-` session cookie is set.
- **Scan:** fail on high or critical findings, the same bar as the dependency audit.
- **Permissions:** `packages: write` only in the publish job; third-party actions pinned by commit SHA as the existing workflow does.

### Compose and docs

`compose.example.yml` (Caddy mode: a `data` volume and a separate backups mount) and a plain-HTTP variant. One new document, `docs/SELF-HOSTING.md`, linked from the README: HTTPS and the homelab fallback, putting it behind your own reverse proxy, upgrades, backups and restore, and the AWS-to-self-hosted data move (the steps already in `docs/ROADMAP.md`, moved or linked).

## 3. Security, failure handling and changes to existing code

### Adapter hardening

A 1 MiB body cap (413 above it); header, request and keep-alive timeouts; the handler's own generic 500 on an unhandled error, detail in the logs only. `x-forwarded-*` is honoured only when `TRUST_PROXY` is on; otherwise the source IP is the socket address.

### Caddy

The Caddyfile is generated only from a validated hostname and email, so no user-typed text is interpolated into configuration. Certificates are stored at `$DATA_DIR/caddy` so they survive restarts and upgrades. The admin API is off; logging goes to stdout; `encode zstd gzip` is on; the HTTP-to-HTTPS redirect is Caddy's default.

### Shutdown

On SIGTERM: stop accepting connections, let in-flight requests and a running backup finish (10-second cap), close SQLite, stop Caddy, exit 0. A failed scheduled backup is logged with the error name only and never crashes the server.

### Changes to existing code (each with tests)

1. `originAllowed` (`src/auth/cookies.ts`) compares against `APP_ORIGIN` exactly when it is set (closes the DNS-rebinding parked item).
2. The session cookie is named `__Host-budget_session` whenever it is `Secure`, and `budget_session` otherwise. A sibling subdomain cannot set a `__Host-` cookie (closes the cookie-tossing parked item). Reading uses the name for the current mode.
3. `SqliteStore.backupTo(path)` using `VACUUM INTO` (a consistent snapshot under WAL that refuses to overwrite an existing file; chosen over `sqlite.backup()` because it is synchronous and never overwrites). The downgrade guard on `user_version` already exists in `SqliteStore.migrate()`; this project adds a test for it and a clear boot message.
4. `store-cli backup --out <file>`: a consistent online copy, owner-only (`0o600`, `flag: 'wx'`), never overwrites.
5. The About page "Source code" link.

### Backups

Daily at `BACKUP_HOUR` in `TZ`, files named `budget-YYYYMMDD-HHMMSS.sqlite`, written owner-only into an owner-only directory. Each copy is verified with `PRAGMA integrity_check` before it counts, so a corrupt backup never causes a good one to be pruned. The newest `BACKUP_KEEP` verified files are kept. A missed run is caught up at the next start.

## 4. Testing

- **Unit:** the environment validation table; the Caddyfile generator (golden output and injection attempts); the adapter (event shape, multi-cookie `Set-Cookie`, base64 bodies, the 413 cap, proxy-trust behaviour); backup retention, integrity checking and catch-up with an injected clock; the downgrade guard; `APP_ORIGIN` matching; the `__Host-` cookie naming; the maintenance timer with fake timers; shutdown.
- **In-process integration:** the real server on an ephemeral port with a temporary database, running setup, login, logout and password reset over `fetch`.
- **Container smoke tests in CI:** as above, both plain HTTP and the `localhost` HTTPS variant.
- **Frontend:** the About-page link.

## Risks and unverified points

- Real Let's Encrypt issuance cannot be tested in CI; only the internal-CA path can.
- The `arm64` image is built under QEMU but smoke-tested on `amd64` only.
- No Docker daemon was available on the author's machine when this spec was written, so the image had never been built or run locally; CI is the first real build.
- scrypt memory on a 256 MB host, and listing on a hosting partner, are untested.
- Binding 80 and 443 as a non-root user relies on a file capability on the Caddy binary. A platform that runs containers with `no-new-privileges` ignores file capabilities, and Caddy then cannot bind; the docs say to use `TLS_DOMAIN`-less plain HTTP behind the platform's own proxy in that case.
- A homelab user on plain HTTP relies on the derived `COOKIE_SECURE` behaviour and the documentation.
- The login throttle is still global: anyone who can reach the login endpoint can lock the owner out for up to 15 minutes (`store-cli reset-password` clears it).
- Same-volume backups do not protect against losing the volume.
